# 22 - 编辑器与渲染库适配失配分析

> 分析日期：2026-08-29
> 分析对象：`packages/new-assembox-editor`（`@cs/assembox-editor-next`）
> 比对基准：`assembox-packages-project/libs/assembox-core-next` + `assembox-desktop-next`（以 `docs/architecture/` 12 篇架构手册与 `review-notes.md` 已拍板结论为准）
> 取证方式：源码逐文件比对 + 关键失配点二次人工验证（事件 actions 格式、YqPanel.toolSlot、inline 路径 adaptNodeTree、setRuntimeConfig 均已到源码行级确认）

---

## 0. 总体判断

编辑器在**静态结构契约**上与渲染库适配良好：

- 节点信封 `IBaseNode`（`__nodeName/__nodeId/__nodeType/__nodeEvent/__nodeOptions/__nodeStyle/__nodeProps`）读写一致；
- 56 个 renderType、暴露方法（methods）清单与 `desktop-next/src/components/manifest.ts` 逐项吻合；
- 嵌套校验直接 import 渲染库 `lookupSlotGate/isCategoryAllowed/lookupMeta` 同源判定（`src/scenarios/pc-desktop/nesting-rules.ts:5`），并配静态镜像表 + 守护测试（`__tests__/nesting-categories.test.ts`）防漂移；
- 数据源面板类型定义与 core 的 request-config 逐字段对齐；
- iframe 画布协议完整（adaptNodeTree / assemBoxIsEdit / AssemVueRenderer / registerDefaults + registerExternal / data-editor-id 选中链路）。

但在**动态行为契约**（事件如何执行、槽位如何消费、画布如何热更新）上存在成体系的失配。其中事件模型是两套设计哲学（动作编排 vs 函数体）的正面碰撞，需要先拍板统一方向；其余多为可快速修复的实现层偏差。

## 1. P0 级：根本性失配

### 1.1 事件模型两套哲学未打通 —— 事件功能整体空转（最严重）

**性质：架构设计分歧，非实现 bug。**

- 编辑器侧（`src/plugins/settings-pane/settings-pane.tsx:15-52`）：EventList 把事件写成 amis 风格的**动作编排**格式：

  ```js
  __nodeEvent[evName] = { actions: [{ actionType: "toast", args: { message: "新动作" } }] }
  ```

  配套自研动作体系 `src/actions/builtin-actions.ts`（toast / navigate / ajax…）。

- 渲染库侧（`assembox-core-next/src/core/adapt-node-tree.ts:118-155`）：`adaptEvents` **只认 `fn: string` 或 `handler: function`**。`{actions}` 两者皆无 → 走 `reportMalformed` 分支，**告警 `EVENT_DEF_MALFORMED` 后整个事件被丢弃**（同文件 167-176 行）。渲染库全库无任何代码消费 `actions` 字段。

**后果链**：属性面板"事件"Tab 配置的每一个事件，在画布预览与生产渲染端**都不会触发**，唯一痕迹是控制台一条 warn。

**同类埋雷**（当前仅注册未接线，但输出格式渲染库同样不认识）：

- `src/setters/js-function-setter/index.tsx:26-32,140-147` 输出 `{type:'JSFunction', params, body}`；
- `src/setters/expression-setter/index.tsx:6-9,55-59` 输出 `{type:'JSExpression', value}`；
- 渲染库对这两个概念全库 grep 零命中，`adaptNodeTree` 不会编译该结构。

**修复方向（二选一，推荐前者）**：

1. 编辑器把动作卡片编排**编译成**渲染库契约格式 `{enabled: true, fn: "function(ctx, payload){ ... }"}`（动作卡片 → 函数体字符串的代码生成），渲染库零改动；
2. 渲染库增加 actions 协议解释器（改动大，且与"事件就是函数"的既定设计冲突，需重开评审）。

### 1.2 YqPanel.toolSlot 数组语义 vs 渲染端单节点直渲 —— 插入即渲染破损

- 编辑器声明为**数组槽**：`src/scenarios/pc-desktop/component-metadata-config/block-container.ts:62`，`{ name: "toolSlot", slotType: "array" }`，且未配组件级白名单，插入动作会把子节点**数组化**写入；
- 渲染端 `assembox-desktop-next/src/components/block-contanier/panel/assem-yq-panel.vue:6-13` 把 `options.toolSlot` 当**单个 YqFlexLine 节点**直读 `options.toolSlot.__nodeOptions` —— 数组化后该取值为 `undefined`，渲染直接破损；
- **双重失守**：渲染库 `nesting.ts` SLOTS 表未登记 YqPanel.toolSlot（模板硬编码直渲不经 NodeRenderer），而编辑器 `canNest` 对未登记槽位返回 `true` 放行（`nesting-rules.ts:31-33`）—— 两侧门禁都没拦住。

**修复**：对齐 `YqToolBar.defaultSlot` 的正确写法（`block-container.ts:94`：object 类型 + `slotRender: ["YqFlexLine"]` 组件级白名单）。另建议在编辑器侧对「SLOTS 未登记但渲染端硬编码直渲」的槽位建立清单，避免下一个同类槽位。

### 1.3 双渲染路径行为分叉：inline 画布缺 adaptNodeTree

- iframe 路径（demo 默认）：`src/simulator/iframe/iframe-canvas-renderer.ts:183` 先 `adaptNodeTree(schema)` 编译事件 handler 再入响应式渲染 ✓
- inline 路径（`src/core/editor.ts` 默认 `canvasMode="inline"`）：`src/scenarios/pc-desktop/renderer.ts` 全程**未调用** `adaptNodeTree`，schema 原样进 `AssemPlugin`（该插件不做适配）—— 函数字符串事件不编译，触发 NodeRenderer 的 `EVENT_NOT_ADAPTED` 告警，**事件在 inline 画布不触发**。

**修复**：PcRenderer 渲染前补调 `adaptNodeTree`，与 iframe 路径对齐；建议抽公共入口防止再次分叉。

### 1.4 setRuntimeConfig 调用了不存在的方法 —— 防御式写法静默吞掉失配

`src/plugins/data-source-pane/doc/use-data-source-doc.ts:79`：

```js
(editor.renderer as any)?.setRuntimeConfig?.({ dataSource: cloneDoc(state) });
```

两个渲染器实现的方法名都是 `setRuntime`（`src/simulator/iframe/pc-iframe-renderer.ts:194`、`src/simulator/iframe/iframe-canvas-renderer.ts:129`；`src/designer/designer-host.tsx:48-49` 调的也是 `setRuntime`）。`as any + ?.` 使该错误**静默降级**：数据源面板编辑后画布永不热更新，无任何报错。

**修复**：改名 `setRuntime`；去掉 `as any` 改走类型化接口（让方法名拼错变编译错误）。**注意第二处断点**：即使改对名字，iframe 侧 `setRuntime` 收到新 dataSource 后目前也不重建 `AssemCore`，热更新链路仍不通，需一并补齐。

## 2. P1 级：结构性风险

### 2.1 `__nodeId` 生成用随机短串，节点寻址语义失效

`src/scenarios/pc-desktop/schema-ops.ts:36` `genNodeId(type)` 生成 `` `${type}::${shortId()}` ``，id 的 name 段是随机串。渲染库的寻址体系是 `ctx.getNode('YqTableAsync::supplierTable')`（精确 id 落空后按 `Type::name` 拆解回退查 `__nodeName`，见 `node-registry.ts:204`）—— 编辑器产出的事件代码只能复制完整随机 id 引用节点，`find({name})` 语义名查找基本失效，与"`__nodeName` 是寻址键"的节点模型设计初衷相悖。

**建议**：`__nodeName` 生成时即用语义 slug（如 `button-3`、`supplier-table`），`__nodeId` 派生自它；面板上提供改名入口并同步重写引用。

### 2.2 model-name-setter / request-fn-setter 数据源 prop 未接线

- `src/setters/model-name-setter/index.tsx:20` 需要 `modelTree` prop；
- `src/setters/request-fn-setter/index.tsx:21-29` 需要 `dataSourceTree/dataSource` prop；
- 全仓库无任何地方传入（settings-pane 只透传 value/defaultValue/fieldName/onChange/setterProps，见 `settings-pane.tsx:265-275`）。

**后果**：绑定 modelName / requestFn 时树形选择器**恒为空**，只能手敲字符串、零校验 → 悬空引用（指向不存在的模型/服务）成为常态。

### 2.3 删除数据服务不扫引用

`src/plugins/data-source-pane/doc/tabs/services-tab.tsx:46-53` 直接删 `requestConfig` 条目；`src/plugins/data-source-pane/models/reference-scan.ts` 只扫模型引用，**不扫节点的 `requestFn` 指向**（渲染库 16 个组件有 `requestFn` 选项）。删掉一个还被表格引用的服务，画布上表格数据加载静默挂掉。

**建议**：reference-scan 增加 `requestFn` / `advancedFilterModelName` 维度扫描；删除前弹引用确认。

### 2.4 事件元数据与 manifest 存在偏差（配置面失真）

用户"配了没反应"、零报错的一类失配：

| 组件 | 编辑器暴露 | manifest 实际 | 证据 |
|---|---|---|---|
| YqLabel / Tag / Image / Icon / RawHtml | `onClick`（Tag/Image 还有 `onClose/onShow`） | 仅 `BasicEvents`（onMounted/onValueRender），这些事件渲染端没有 dispatch 点 | `line-display.ts:54,85-87,131-133,152,169` vs `manifest.ts:240-246` |
| YqTableTree | 自定义 `onTreeLoad/onSummaryMethod`，漏 onRowClick/onSortChange/onExpandChange 等 | `TableLikeEvents` 标准集 | `element-table.ts:173-180` vs `manifest.ts:416-425` |
| FormItem | events 为空 | 有 BasicEvents | `line-input.ts:358` |
| TimePicker | 漏 `onLoadData` | manifest 有 | `manifest.ts:302-306` |

另：`fn-editor.tsx:23` 的速查示例 `'TableAsync::name'` 是不存在的 renderType（应为 `YqTableAsync`），会教错用户。

**建议**：仿照 `nesting-categories.test.ts` 的做法，为事件元数据加一个与 manifest `NodeEventConfigMapFromManifest` 的对齐守护测试；速查文案修正。

## 4. 已确认一致、无需动作的项（防止重复排查）

- **renderType 全集**：除 Plane/Dialog/Drawer（视图层按契约豁免，`layer.ts:9-74`，面板已过滤 Plane）与 UiSkeletonBlockSlot（有意不暴露）外，55 项一一对应、拼写一致。
- **methods（暴露方法）清单**：表格族/列表族/选项类/字典族/Form/Chart/DatePicker 与 manifest exposed 全部吻合（`element-table.ts`、`shared.ts:76-125` vs `manifest.ts:148-196,399-536`）。编辑器当前无运行时调用 expose 方法的代码，未来经 `ctx.getNode(id).exposed.xxx` / `ctx.call(...)` 调用时名称可用（但受 2.1 随机 id 制约）。
- **数据源面板核心契约**：`paramsType/dataModelType/dataModelName/advancedFilterModelName/paramsModel`、`beforeReq/afterReq = {enabled, fn}`、sharedFns `{enabled, fn}`、resolveType 逗号多值（库侧 `.includes()` 消费）、isOn→enabled 读兼容写归一 —— 与 `core-next/src/types/datasource/*` 及 `adapt-node-tree.ts:134` 逐项对齐。
- **iframe 画布协议**：UMD/ESM 双载入、`assemBoxIsEdit/assemBoxDesignMode`（`iframe-canvas-renderer.ts:72-74`）、`window.AssemVueRenderer` 三回调（208-212）、`AssemPlugin + registerDefaults()`（322-323）、按资产清单 `registerExternal`（326-341）。
- **嵌套校验三级优先**（组件级白名单 → SLOTS 门禁 → category 静态表 + 库运行时兜底）：设计合理，iframe 模式下 host 副本未注册导致 `lookupMeta` 恒 undefined 的场景已由静态表覆盖。
- **多槽位识别**：不走 DOM 标记，`slot-dom/resolveSlotKeyFromDom` 几何解析，与渲染库 `use-editor.ts:80-82` 的注释分工一致。

**编辑器侧存在但渲染库零消费、被运行时忽略的字段**（记录在案，低优先）：`DsServiceItem.isTopUp`（`doc/types.ts:72`）、`paramsConfig.paginationConfig`（`types.ts:60`、`normalize.ts:85`）、`api.list` 旧版透传（`types.ts:106`、`normalize.ts:101` —— 库 `DataSource.api` 类型只有 `config`）。

## 5. 修复优先级路线

| 优先级 | 问题 | 动作 | 验证方式 |
|---|---|---|---|
| ① | 事件 actions 格式被渲染库丢弃（1.1） | 拍板方向：推荐编辑器把动作卡片编译成 `{enabled, fn}` 函数体；顺带处理 JSFunction/JSExpression setter 的产出格式 | 端到端：编辑器配 toast 动作 → 画布触发 → 生产 JSON 渲染触发；控制台无 EVENT_DEF_MALFORMED |

| ⑥ | 事件元数据偏差 + 随机 __nodeId + 脏数据（2.1/2.4/3.x） | 加事件元数据对齐守护测试；__nodeName 语义化；清理 contentType/tabOptions/isRow/tag | 守护测试进 CI；新旧场景 diff 无脏键 |
