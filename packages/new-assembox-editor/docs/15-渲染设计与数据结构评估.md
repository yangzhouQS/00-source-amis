## 一、两份 Schema 的结构对比

### 1.1 顶层骨架（两份一致）

```
Root
├── uiSkeleton              ← 编辑器 schema（唯一操作对象）
│   └── <场景名>            ← 场景 = 一个页面
│       └── viewsProps
│           ├── planeOptions     ← 主视图树
│           ├── dialogOptions[]  ← 弹窗文档树（single-table 有，order-table 无）
│           ├── drawerOptions[]  ← 抽屉文档树（推测）
│           └── ...
├── routerConfig            ← 路由表（不可编辑）
└── dataSource              ← 数据层（不可编辑）
    ├── api.config
    ├── requestConfig
    ├── dataModelConfig
    └── sharedFns
```

### 1.2 关键差异

| 维度                    |  single-table-scene  |                order-table-config                |
| ----------------------- | :------------------: | :----------------------------------------------: |
| 场景数                  |   1（singleTable）   |   **3**（orderList / orderDetail / orderEdit）   |
| dialogOptions           | ✅ 有（Dialog 弹窗） |                      ❌ 无                       |
| 跨页跳转                |  无（Dialog 打开）   | ✅ `ctx.$globalVars.$router.push('/order-edit')` |
| TabPanel                |          无          |            ✅ `tabPane[]` 两个标签页             |
| ButtonGroup             |          无          |            ✅ `buttonGroupOptions[]`             |
| TableEdit（可编辑表格） |          无          |                ✅ orderEdit 中有                 |
| nodeType 种类           |      renderNode      |      **renderNode + baseNode + columnNode**      |

### 1.3 编辑器当前只认第一个场景

`renderer.ts:67-68`：

```typescript
const scenes = Object.values(this.schema || {});
const scene = scenes[0];   // ← 硬编码取第一个场景
```

`main.tsx:45`：

```typescript
schema: (schemaJson as any).uiSkeleton,  // ← 传整个 uiSkeleton（含多场景）
```

**结果**：order-table-config 传入 3 个场景，渲染器只画 `orderList`，`orderDetail` 和 `orderEdit` 在画布上不可见。

## 二、节点类型体系

两份 JSON 中出现 **3 种 `__nodeType`**：

|  __nodeType  | 用途             | __nodeId 格式                | 额外字段                     | 示例                                 |
| :----------: | ---------------- | ---------------------------- | ---------------------------- | ------------------------------------ |
| `renderNode` | 标准渲染节点     | `Type::name`（带 `::`）      | —                            | Button / FlexBox / Toolbar           |
|  `baseNode`  | 基础节点         | `rawHtml_xxx`（无 `::`）     | `__nodeKey`、`__description` | RawHtml                              |
| `columnNode` | 表格可编辑单元格 | `inputNumber_xxx`（无 `::`） | `__nodeKey`、`__description` | InputNumber / Select（TableEdit 列） |

**编辑器只识别 `renderNode`**。`baseNode` 和 `columnNode` 出现在 `opts.tabPane[]` / `opts.columnSlots[]` 内，本就处于遍历盲区（见下文第三节），即使进入遍历也缺乏类型适配。

## 三、核心发现：槽位容器全景与遍历盲区

### 3.1 槽位的两种存储模式

两份 JSON 中，子节点的存储位置存在**两种模式**：

**模式 A — 直接槽位**：子节点直接挂在 `__nodeOptions.<字段>` 上

```
Toolbar.__nodeOptions.toolSlot = [ <Button>, <Button> ]
Toolbar.__nodeOptions.filterSlot = [ <FilterItem>, ... ]
Box.__nodeOptions.defaultSlot = <子节点>
```

**模式 B — 间接槽位**：子节点包裹在中间配置数组的某个属性里

```
FlexBox.__nodeOptions.itemConfig[i].defaultSlot = <子节点>
TabPanel.__nodeOptions.tabPane[i].defaultSlot = <子节点>
ButtonGroup.__nodeOptions.buttonGroupOptions[i].buttonOption = <子节点>
TableAsync.__nodeOptions.columnSlots[i].columRender = <子节点>
```

### 3.2 槽位容器完整清单

| # | 容器字段 | 宿主组件 | 存储模式 | 数据路径 | walk 覆盖 |
|:-:|---------|---------|::-:|------|::-:|
| 1 | `defaultSlot` | 通用 | A | `opts.defaultSlot` | ✅ |
| 2 | `toolSlot` | Toolbar | A | `opts.toolSlot[]` | ✅ |
| 3 | `filterSlot` | Toolbar | A | `opts.filterSlot[]` | ✅ |
| 4 | `headerSlot` | Panel | A | `opts.headerSlot` | ✅ |
| 5 | `bottomSlot` | Panel | A | `opts.bottomSlot` | ✅ |
| 6 | `rightSlot` | FlexLine | A | `opts.rightSlot[]` | ✅ |
| 7 | `itemConfig` | FlexBox | **B** | `opts.itemConfig[].defaultSlot` | ✅ 特殊分支 |
| 8 | `tabPane` | TabPanel | **B** | `opts.tabPane[].defaultSlot` | ❌ **盲区** |
| 9 | `buttonGroupOptions` | ButtonGroup | **B** | `opts.buttonGroupOptions[].buttonOption` | ❌ **盲区** |
| 10 | `columnSlots` | Table 系列 | **B** | `opts.columnSlots[].columRender` | ❌ **盲区** |
| 11 | `dialogOptions` | viewsProps | B | `viewsProps.dialogOptions[]` | ❌ **盲区** |
| 12 | `dropdownItem` | Dropdown | — | `opts.dropdownItem[]`（纯配置，非节点） | — 正确跳过 |

### 3.3 walk 盲区的根因

`schema-ops.ts:75-103` 的 walk 逻辑：

```typescript
walkNode(node, parent, slotKey) {
  visitor(node, parent, slotKey);
  const opts = node.__nodeOptions;

  // ① 直接槽位：遍历 SLOT_FIELDS，取 opts[field]
  for (const field of SLOT_FIELDS) {        // SLOT_FIELDS 含 columRender、buttonOption
    const val = opts[field];                // ← opts.columRender / opts.buttonOption
    ...                                      //    但实际数据在 opts.columnSlots[].columRender
  }                                          //    和 opts.buttonGroupOptions[].buttonOption

  // ② FlexBox 间接槽位：唯一特殊处理
  if (Array.isArray(opts.itemConfig)) {
    opts.itemConfig.forEach(item => walkNode(item.defaultSlot, ...));
  }
}
```

**SLOT_FIELDS 里的 `columRender` 和 `buttonOption` 是"幽灵槽位"**——它们被列入列表，但实际 JSON 中从不存在 `opts.columRender` / `opts.buttonOption` 这样的直接属性，真实路径是嵌套的。因此这两个字段的遍历代码**永远不执行**。

**根遍历**（`schema-ops.ts:105-111`）：

```typescript
for (const scene of scenes) {
  const root = scene?.viewsProps?.planeOptions;
  if (root) walkNode(root, null, "defaultSlot");
  // ← dialogOptions / drawerOptions 完全未遍历
}
```

### 3.4 盲区影响实测

以 `order-table-config.json` 的 `orderList` 场景为例：

| 盲区                 | 受影响节点                                                                                 | 后果                                                 |
| -------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `dialogOptions`      | （此文件无）                                                                               | —                                                    |
| `tabPane`            | TabPanel 内的 `TableNext::order-table`（点收单）、`ListNext`（列表展示）及它们的全部子节点 | **两个标签页内容在大纲树不可见、不可选中、不可编辑** |
| `buttonGroupOptions` | `Button::button_print`、`Button::button_export`（打印/导出按钮）                           | **按钮组内的按钮不可编辑**                           |
| `columnSlots`        | Tag::tag-status、Button::button（单据编号链接）、Tag::tag-service-type 等                  | **表格单元格渲染器不可编辑**                         |

> `single-table-scene.json` 同理：`Dialog::supplierDialog` 整棵子树（Form → GridBox → FormItem → Input，约 15 节点）因 `dialogOptions` 盲区完全不可编辑。

## 四、渲染设计评估

### 4.1 当前管线

```
Editor.start()
  → Store（reactive schema = uiSkeleton）
  → DesignerHost.mount()
    → PcRenderer.mount(container, schema)
      → createApp → <AssemViews viewsProps={scenes[0].viewsProps}/>
      → app.use(AssemPlugin, { uiSkeleton: schema })
```

### 4.2 评估

| 维度                     |  结论   | 说明                                                              |
| ------------------------ | :-----: | ----------------------------------------------------------------- |
| schema = 运行时配置      | ✅ 正确 | 零转换，编辑器直接操作 AssemPlugin 的 uiSkeleton                  |
| reactive 引用桥接        | ✅ 合理 | Store.schema 与 renderer 同引用，setSchema 保持引用               |
| 结构变更 vs 属性更新分离 | ✅ 合理 | insert/move/remove → setSchema 全量同步；updateProps → 原地 patch |
| DOM 标记体系             | ✅ 标准 | data-editor-id / data-slot-host / data-slot-key                   |
| `scenes[0]` 硬编码       | ❌ 缺陷 | 多页场景只渲染第一页，无场景切换能力                              |
| window 全局桥            | ⚠️ 脆弱 | assemBoxIsEdit / assemBoxDesignMode 污染全局，不支持多实例        |

### 4.3 渲染设计结论

**渲染管线架构正确，不需要重构。** "schema-as-config"策略是核心优势——编辑器直接操作运行时格式，消除了编辑格式↔运行时格式的转换层及往返保真度问题。需要优化的是**场景选择**（替代 scenes[0] 硬编码）和**全局桥**（改 DI 注入），这些是局部改动，不涉及架构重构。

## 五、关键数据结构评估

### 5.1 节点信封结构

```typescript
{
  __nodeName: "supplierToolbar",
  __nodeId:   "Toolbar::supplierToolbar",
  __nodeType: "renderNode",
  __nodeEvent: { onClick: { enabled, fn } },
  __nodeOptions: { renderType, defaultSlot, ...props },
  __nodeStyle: {},
  __nodeProps: null,   // ← 恒为 null，全量无读取，死字段
}
```

### 5.2 评估

| 结构                          |     结论      | 理由                                         |
| ----------------------------- | :-----------: | -------------------------------------------- |
| `__node*` 信封                |    ✅ 保留    | assembox-desktop-next 运行时格式，改了就脱节 |
| 槽位内嵌 `__nodeOptions`      |    ✅ 保留    | 运行时约定，slot 即组件属性                  |
| `__nodeId` 格式 `Type::name`  |    ✅ 保留    | 人类可读，调试友好                           |
| FlexBox `itemConfig` 间接结构 |    ✅ 保留    | 布局原语固有复杂度                           |
| snapshot 历史                 | ✅ 当前可接受 | 小规模够用                                   |
| `__nodeProps` 死字段          |    🧹 清理    | 恒 null，无读取逻辑                          |
| SLOT_FIELDS 硬编码            |   ⚠️ 需重构   | 见 5.3                                       |

### 5.3 SLOT_FIELDS 机制的根本缺陷

当前 walk 的遍历策略是：**枚举一个字段名列表，逐个检查 `opts[field]` 是否存在**。这个策略有两个根本问题：

**问题 1：无法表达间接路径。** 模式 B 的间接槽位（tabPane / buttonGroupOptions / columnSlots）需要"取数组 → 取数组元素 → 取元素内某属性"的多级路径，扁平的 `opts[field]` 查询无法表达。FlexBox 的 itemConfig 是通过硬编码特殊分支（`schema-ops.ts:96-102`）解决的，但同类的 tabPane / buttonGroupOptions / columnSlots 没有得到同样处理。

**问题 2：槽位名与数据路径不一致。** `columRender` 和 `buttonOption` 出现在 SLOT_FIELDS 列表中，暗示它们是"槽位"，但实际 JSON 中它们从不作为 `__nodeOptions` 的直接属性出现——真实路径分别是 `columnSlots[].columRender` 和 `buttonGroupOptions[].buttonOption`。这导致遍历代码永远匹配不到。

### 5.4 数据结构结论

**节点信封不需要重构**（它是运行时格式）。**槽位遍历机制需要重构**——当前的"扁平字段枚举 + 单一 itemConfig 特例"无法覆盖生产 schema 中的 4 种间接容器，导致系统性遍历盲区。

## 六、结论与建议

### 是否需要重构数据结构？

| 对象                  | 结论                                      |
| --------------------- | ----------------------------------------- |
| 节点信封（`__node*`） | **不重构** — 运行时格式                   |
| 槽位内嵌方式          | **不重构** — 运行时约定                   |
| 槽位遍历机制          | **需重构** — 从"扁平枚举"改为"路径规则表" |
| 渲染管线              | **不重构** — 架构正确                     |
| 场景选择              | **需优化** — 替代 scenes[0] 硬编码        |

### 核心改动方向：槽位遍历规则化

将间接容器的遍历从"散落的硬编码 if 分支"统一为**声明式规则表**：

```typescript
// 每条规则描述一种容器的"如何取子节点"
interface SlotAccessor {
  slotKey: string;                              // 槽位名（用于 nesting + 大纲）
  label: string;
  getChildren: (opts: any) => any[];            // 从 __nodeOptions 取子节点数组
  addChild: (opts: any, node: any, index?: number) => void;  // 插入
  removeChild: (opts: any, nodeId: string) => any;           // 移除
}

// 直接槽位（模式 A）
const directSlots: SlotAccessor[] = [
  { slotKey: "defaultSlot", label: "内容区", getChildren: opts => asArray(opts.defaultSlot), ... },
  { slotKey: "toolSlot",    label: "工具栏", getChildren: opts => opts.toolSlot ?? [], ... },
  // ...
];

// 间接槽位（模式 B）——按 renderType 注册
const indirectSlots: Record<string, SlotAccessor[]> = {
  FlexBox:     [{ slotKey: "defaultSlot", getChildren: opts => opts.itemConfig?.map(i => i.defaultSlot).filter(Boolean) ?? [], ... }],
  TabPanel:    [{ slotKey: "defaultSlot", getChildren: opts => opts.tabPane?.map(t => t.defaultSlot).filter(Boolean) ?? [], ... }],
  ButtonGroup: [{ slotKey: "buttonOption", getChildren: opts => opts.buttonGroupOptions?.map(b => b.buttonOption).filter(Boolean) ?? [], ... }],
  TableAsync:  [{ slotKey: "columRender", getChildren: opts => opts.columnSlots?.map(c => c.columRender).filter(Boolean) ?? [], ... }],
};
```

这样 walk / insert / remove / findSlotOf 全部统一走规则表，新增组件槽位只需注册一条规则，不再需要改 walk 逻辑。

### 优化优先级

| 优先级 | 改动                                                                                     | 影响                                  |  量级   |
| :----: | ---------------------------------------------------------------------------------------- | ------------------------------------- | :-----: |
| 🔴 P0  | walk 补全 4 个间接容器遍历（tabPane / buttonGroupOptions / columnSlots / dialogOptions） | 当前生产 schema 中大量节点不可编辑    | ~60 行  |
| 🔴 P0  | walk 根遍历补 dialogOptions / drawerOptions                                              | Dialog 弹窗整棵子树不可编辑           | ~10 行  |
| 🟠 P1  | 槽位遍历规则化（SlotAccessor 表）                                                        | 消除硬编码 if 分支，新增槽位零改 walk | ~150 行 |
| 🟠 P1  | 渲染器场景选择（替代 scenes[0]）                                                         | 多页路由场景可切换编辑                | ~40 行  |
| 🟡 P2  | commit 单次克隆（store.ts）                                                              | 大 schema 性能                        | ~10 行  |
| 🟢 P3  | 清理 __nodeProps 死字段                                                                  | 代码整洁                              |  ~5 行  |
