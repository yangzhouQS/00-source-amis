# 渲染可控性可行性方案：编辑器复用 assembox-desktop 渲染

> 背景：旧版 `assembox-editor` 直接调用 `assembox-core` + `assembox-desktop` 渲染那套复杂嵌套 JSON。
> 痛点：**编辑器对渲染过程可控性极差，差异化重渲染几乎不可控**。
> 约束：① 需继续使用该 JSON 结构；② 编辑器仅开发期使用；③ 编辑器渲染行为必须与生产一致；④ 生产运行时只用 `assembox-desktop`。

---

## 一、现状诊断：为什么「不可控」

### 1.1 渲染是「按 renderType 的黑盒递归派发」

`assembox-desktop` 的渲染核心是两个递归派发器：

```
container-render.vue   →  containerRegistComs[__nodeOptions.renderType]   (toolbar/panel/box...)
element-render.vue     →  elementRegistComs[__nodeOptions.renderType]     (button/input/table...)
```

每个派发器**剥一层包装**（`containerOptions`/`elementOptions` → 取出内层 baseNode 的 `__nodeOptions/__nodeEvent/__nodeId`），交给注册组件。注册组件（box/panel/button...）自己渲染并对其 `defaultSlot` **再次递归**派发。

**后果**：整棵树是「一次全量自递归」，对外没有任何「单节点拦截点」。编辑器把整份 JSON 丢给 `views`，渲染器一口气渲染完，编辑器拿不到任何中间控制权。

### 1.2 `isEditorEnv()` 只是个「外壳开关」，不是「节点缝」

`container-render.vue` / `element-render.vue` 里的 `isEditorEnv()` 只是：

```vue
<div v-if="isEditorEnv()" class="editor-container-render">
  <component :is="current" ... />
</div>
```

它只在外层多包一个带 class 的 `<div>`。**没有任何能力**：
- 给每个节点打标记（`data-editor-id`）；
- 捕获每个节点的 DOM ref / 组件实例；
- 给节点绑定点击/悬浮（选中/高亮）；
- 在节点外层套编辑器控制层（选区框/工具栏）。

### 1.3 节点缺稳定身份 → Vue keyed diff 失效 → 全量重渲染

- `__nodeId` **大量重复**（box.json 19 个 id 仅 13 个唯一）；
- 递归渲染 `defaultSlot.map(...)` **没有 key**；
- 结果：改动一个按钮的文字，Vue 无法按 key 定位差异，**整棵子树卸载重建** → 组件内部状态丢失、闪烁、卡顿。

这就是「差异化重新渲染几乎不可控」的根因：**不是没有响应式，而是没有稳定节点身份**。

### 1.4 编辑器要的「控制」清单（目前全缺）

| 编辑器需要 | 现状 |
|---|---|
| 给节点打 `data-editor-id`（选中/DOM 定位） | ❌ 无缝 |
| 捕获节点 DOM ref / 实例（几何测量、BemTools） | ❌ 无缝 |
| 单节点点击/悬浮 → 选区/高亮 | ❌ 无缝 |
| 差异化重渲染（改一个属性只重渲染该节点） | ❌ 全量重建 |
| 节点树镜像（大纲/拖拽投放判定） | ❌ 无缝 |
| 拖拽投放位置计算（region/index） | ❌ 无 region |

## 二、核心约束与本质

1. **渲染一致性是硬约束**：编辑器看到的样子 == 生产 `assembox-desktop` 渲染的样子。→ **编辑器必须复用 `assembox-desktop`，不能另写一套渲染器**（否则两套实现必然漂移）。
2. **生产零开销**：`assembox-desktop` 在生产是「纯净渲染器」，任何编辑器能力都**不能**污染生产路径。
3. **JSON 要继续用**：存量配置 + 生产解析都依赖该结构，短期内不能废弃。

**矛盾本质**：`assembox-desktop` 是「黑盒全量渲染器」，而编辑器需要「白盒逐节点控制」。二者之间缺一个**仅在编辑期激活的「设计缝（design seam）」**。

> 类比：amis 用 `env.rendererResolver` + `makeWrapper`；lowcode 用 `customCreateElement` + `onCompGetRef`。这些都是「渲染器留给编辑器的注入点」，生产环境为 no-op。**assembox-desktop 目前缺这一层。**

## 三、可行性方案对比

### 方案 A：渲染器注入式「设计钩子」（design hooks）★推荐

给 `assembox-desktop` 增加**可选的设计钩子**，仅在编辑环境激活，生产为 no-op。

**核心 API（生产零侵入）**：
```ts
// assembox-desktop 暴露：注册设计钩子
registerDesignHooks({
  // 包裹每个节点的 VNode（编辑器套选区/标记层）
  wrapNode(meta, vnode): vnode,
  // 提供稳定 key（修复差异化渲染）
  nodeKey(meta): string,
  // 节点挂载/卸载回调（构建节点树镜像）
  onNodeMount(meta, el, instance): void,
  onNodeUnmount(meta): void,
  // 几何查询（BemTools 定位）
  getRect(meta): DOMRect | null,
});
```

`container-render`/`element-render` 在派发时：
```ts
let vnode = h(current, props);
const hooks = getDesignHooks();        // 生产返回 undefined → 直接用原 vnode
if (hooks) vnode = hooks.wrapNode(meta, vnode);  // 编辑器包裹
```

**优点**：
- ✅ 编辑器完全复用 `assembox-desktop` → 渲染**绝对一致**；
- ✅ 生产零开销（hooks 不存在即原路径）；
- ✅ 拿到逐节点控制（标记/ref/选区/几何）；
- ✅ 配合 `nodeKey` 修复差异化渲染；
- ✅ 与 new-assembox-editor 的 BemTools/Dragon/Bridge 天然契合。

**代价**：需改造 `assembox-desktop`（最小化，见第五节）。

### 方案 B：双 Schema + 双向转换器

编辑器在「标准化中间 schema（amis 风格 type/$$id/body）」上工作；渲染前转换回旧 JSON 喂给 `assembox-desktop`。

```
旧 JSON  ──load──►  标准化 schema（编辑）  ──render前──►  旧 JSON  ──►  assembox-desktop
```

**优点**：编辑器脱离旧结构的脏乱；属性面板/大纲/拖拽全部标准化。
**缺点**：
- ❌ 双向转换有 **round-trip 保真风险**（defaultSlot 三态、布局交织难无损往返）；
- ❌ 每次编辑→渲染都要转换，性能/复杂度上升；
- ❌ 仍未解决「逐节点控制缝」（转换后还是黑盒渲染）。
**定位**：可作为 A 的补充（编辑态用标准化 schema 提升体验），但**不能单独解决可控性**。

### 方案 C：稳定 key + 响应式定点变更

不改造渲染器逻辑，只：
1. 加载时**归一化 `__nodeId`**（去重，全局唯一）；
2. 递归渲染处补 `:key="__nodeId"`；
3. 编辑器**就地响应式变更**深路径属性 → Vue 按 key 差异化重渲染。

**优点**：改动最小，立刻解决「全量重建」痛点。
**缺点**：
- ⚠️ 仍缺节点标记/选区/几何缝（选中、BemTools 还是没法做）；
- ⚠️ `defaultSlot` 三态使 key 注入点不统一。
**定位**：是 A 的**必要前置**（无论哪种方案，稳定身份都得先修）。

### 方案 D：iframe 隔离 + assembox-desktop 内嵌

把 `assembox-desktop` 跑在 iframe 内（new-assembox-editor 已有 iframe 能力），编辑器经 Bridge 控制。

**优点**：样式/全局隔离，编辑器与渲染解耦，跨域可控。
**缺点**：单独用 D **仍解决不了逐节点控制**（assembox-desktop 在 iframe 里还是黑盒）。必须叠加 A。
**定位**：作为 A 的**运行容器**（隔离 + 通信），与 A 组合最佳。

### 方案选型矩阵

| 需求 | A 钩子 | B 转换 | C key | D iframe |
|---|:---:|:---:|:---:|:---:|
| 渲染与生产一致 | ✅ | ✅ | ✅ | ✅ |
| 逐节点标记/选区 | ✅ | ❌ | ❌ | ❌ |
| 差异化重渲染 | ✅ | ⚠️ | ✅ | ❌ |
| 几何/BemTools | ✅ | ❌ | ❌ | ❌ |
| 生产零开销 | ✅ | ✅ | ✅ | ✅ |
| 改动量 | 中 | 大 | 小 | 中 |

**推荐：A（设计钩子）+ C（稳定 key 前置）+ D（iframe 容器）组合**，B 作为可选增强。

## 四、推荐方案总体架构

```
┌─ 编辑器（new-assembox-editor，仅开发期） ────────────────────────────┐
│  Workbench / 组件面板 / 属性面板 / 大纲 / BemTools / Dragon           │
│  IframeBridge ──postMessage/直引──┐                                  │
└───────────────────────────────────┼─────────────────────────────────┘
                                     ▼
┌─ iframe 画布（canvas.html）─────────────────────────────────────────┐
│  registerDesignHooks({ wrapNode, nodeKey, onNodeMount, getRect })   │
│         │（编辑期注入；生产不注入 = no-op）                            │
│         ▼                                                            │
│  assembox-desktop (views/substrate)  ←─ 复用，渲染行为与生产完全一致   │
│   ├ container-render / element-render（按 renderType 派发）           │
│   │   └─ hooks.wrapNode(meta, vnode)  ← 每节点被编辑器包裹            │
│   └ 注册组件 box/panel/button/table...                                │
│  assembox-core (AssemCore: $dataModels/$requestFns/$exposeds)        │
└─────────────────────────────────────────────────────────────────────┘
```

生产环境：直接 `AssemPlugin.install(Vue, config)`，**不注册 design hooks** → assembox-desktop 走原路径，零开销。

## 五、`assembox-desktop` 最小改造清单（设计缝）

### 5.1 新增 design hooks 注册口

```ts
// assembox-desktop/src/design-hooks.ts（新增）
export interface DesignHooks {
  wrapNode?: (meta: NodeMeta, vnode: VNode) => VNode;
  nodeKey?: (meta: NodeMeta) => string | number;
  onNodeMount?: (meta: NodeMeta, el: HTMLElement, instance: any) => void;
  onNodeUnmount?: (meta: NodeMeta) => void;
  getRect?: (meta: NodeMeta) => DOMRect | null;
}
export interface NodeMeta { __nodeId: string; __nodeName: string; renderType?: string; }
let hooks: DesignHooks | undefined;
export function registerDesignHooks(h: DesignHooks) { hooks = h; }
export function getDesignHooks() { return isEditorEnv() ? hooks : undefined; } // 生产 no-op
```

### 5.2 派发器接入钩子（container-render / element-render）

```ts
// container-render.vue setup
import { h as hFn, withDirectives } from 'vue';
import { getDesignHooks } from '../../design-hooks';

const render = () => {
  const inner = h(current, { /* 原 props */ });
  const hk = getDesignHooks();
  const meta = { __nodeId, __nodeName, renderType: __nodeOptions?.renderType };
  return hk?.wrapNode ? hk.wrapNode(meta, inner) : inner;
};
```

### 5.3 稳定 key（修复差异化渲染）

在所有递归渲染 `defaultSlot` 的注册组件里，给子节点加 `:key`：
```vue
<container-render v-for="(child, i) in defaultSlot" :key="child.__nodeId ?? i" ... />
```
配合「加载时归一化 `__nodeId` 唯一」，Vue 即可差异化重渲染。

### 5.4 `isEditorEnv()` 复用

钩子仅在 `isEditorEnv()` 生效；生产环境 `getDesignHooks()` 恒返回 `undefined` → 原路径。

> 改造量评估：1 个新文件（design-hooks.ts）+ 2 个派发器接入 + 注册组件补 key。**不改变任何生产行为。**

## 六、编辑器侧集成（new-assembox-editor）

iframe renderer entry（canvas.html）中：
```ts
import { registerDesignHooks } from '@cs/assembox-desktop';
import { createApp } from 'vue';
import { AssemPlugin, views } from '@cs/assembox-desktop';

registerDesignHooks({
  nodeKey: (meta) => meta.__nodeId,                       // 稳定 key
  wrapNode: (meta, vnode) => wrapWithEditorLayer(meta, vnode), // 套选中/标记层
  onNodeMount: (meta, el) => hostApi.onNodeMount(meta.__nodeId, el), // 上报节点树
  onNodeUnmount: (meta) => hostApi.onNodeUnmount(meta.__nodeId),
  getRect: (meta) => hostApi.getRect(meta.__nodeId)
});
// 挂载 assembox-desktop 渲染
const app = createApp({ render: () => h(views, { uiSkeleton, dataSource }) });
app.use(AssemPlugin, { uiSkeleton, dataSource });
app.mount('#app');
```

`wrapWithEditorLayer` 套一个轻量包装组件：
- 设 `data-editor-id=${__nodeId}`；
- 捕获 ref → `onNodeMount`；
- 绑定 click/mouseover → 经 hostApi 回报编辑器（选中/悬浮）。

**差异化更新**：编辑器改属性时，**就地响应式变更** JSON 深路径（AssemCore/props 本就是 reactive）→ Vue 按 `nodeKey` 只重渲染该节点。无需整树重建。

**选中/BemTools/拖拽**：复用 new-assembox-editor 已有的 Dragon + CanvasSensor + BemTools（`getRect` 经钩子取真实几何）。

## 七、继续使用旧 JSON 的优化清单（不改结构的增量优化）

| # | 优化 | 收益 |
|---|---|---|
| 1 | 加载时归一化 `__nodeId`（去重 + 全局唯一映射表） | 选中/引用/keyed diff 可靠 |
| 2 | 递归渲染补 `:key` | 差异化重渲染（解决全量重建） |
| 3 | 注入 design hooks 缝（第五节） | 逐节点标记/选区/几何 |
| 4 | `defaultSlot` 解析统一为「数组归一」适配器 | 子树遍历稳定（不改原 JSON，只在读取层归一） |
| 5 | 事件 `fn` 字符串 → 声明式动作（`onEvent.actions`）增量迁移 | 安全/可校验/可编排（新节点优先） |
| 6 | UI(`uiSkeleton`) 与数据(`dataSource`) 在编辑器内分两个 store 管理 | 独立编辑、独立联调 |
| 7 | 节点路径索引 `Map<id, {parent, region, index}>`（onNodeMount 构建） | 编辑器快速定位/变更深节点 |

> 这些优化**不要求改 JSON 文件本身**，只在「渲染器缝 + 编辑器读取层」做增量，向后兼容存量配置。

## 八、可行性与风险

### 可行性结论：✅ 高度可行

- 复用 `assembox-desktop` 保证一致性 → 满足硬约束；
- design hooks 是「只在编辑期激活的缝」，生产 no-op → 满足零开销；
- 稳定 key + 响应式变更 → 解决差异化渲染；
- new-assembox-editor 的 iframe/Dragon/BemTools 已就绪 → 直接对接。

### 主要风险与对策

| 风险 | 对策 |
|---|---|
| `assembox-desktop` 改动影响生产 | 钩子严格 `isEditorEnv()` 门控；生产集成测试；改动隔离在 design-hooks.ts |
| `defaultSlot` 三态导致 key/wrap 注入不一致 | 读取层「数组归一」适配器统一处理 |
| `__nodeId` 归一化破坏 `$exposeds.get(id)` 引用 | 归一化时维护 `旧id→新id` 映射，转换引用 |
| 事件 `fn` 字符串无法纯声明式迁移 | 增量迁移：新节点用声明式，旧节点降级为 `script` 动作 |
| iframe 内 assembox-desktop 体积大 | 生产仍用原集成方式；编辑器 iframe 独立加载，不影响生产包 |

### 迁移路线图

1. **P0（解锁可控性）**：assembox-desktop 加 design hooks 缝 + 稳定 key + id 归一化 → 编辑器获得逐节点控制与差异化渲染。
2. **P1（编辑器对接）**：new-assembox-editor iframe 内嵌 assembox-desktop + 注册 hooks；BemTools/Dragon 经 hooks 取几何/节点。
3. **P2（体验增强）**：defaultSlot 读取层归一；事件声明式增量迁移；UI/数据 store 分离。
4. **P3（可选）**：双 schema 转换器（标准化中间态）提升编辑体验。

---

## 九、一句话结论

**可控性差的根因不是 JSON 结构本身，而是 `assembox-desktop` 缺一个「编辑期激活的逐节点设计缝」+ 节点缺稳定身份。**
给渲染器加一个生产零侵入的 design hooks（`wrapNode/nodeKey/onNodeMount/getRect`）+ 归一化 id + 补 key，即可在不废弃旧 JSON、保证渲染一致的前提下，让编辑器获得完整的逐节点控制与差异化重渲染能力，并直接对接 new-assembox-editor 已有的画布/拖拽/覆盖层体系。
