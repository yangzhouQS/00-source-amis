# 新版编辑器数据源配置插件 —— 调研分析与完整设计文档

> **版本**：v1.1（设计稿；v1.1 变更：**废弃独立「接口」Tab，接口与服务合并为单一「服务」配置** —— 实际使用中接口几乎不存在跨服务复用，独立登记表徒增维护成本）
> **分析输入**：
> - demo 数据：`single-table-scene.json`（1 场景/4 请求/4 模型/1 共享函数）、`order-table-config.json`（3 场景/8 请求/6 模型/7 共享函数）、`ledger-config.json`（2 场景/7 请求/13 模型/15 共享函数）
> - 渲染层契约：`assembox-core-next`（`request/transform.ts`、`request/merge.ts`、`request/container.ts`、`request/pagination.ts`、`core/data-model-builder.ts`、`core/shared-fn-loader.ts`、`types/datasource/*`）
> - 旧版插件：`assembox/packages/assembox-editor/src/plugins/plugin-data-source`（4644 行）
> - 新版编辑器：`new-assembox-editor`（core/skeleton/setters/plugins 体系）
>
> **结论先行**：插件上下文**基本满足**数据源配置插件的实现（骨架面板、Monaco、事件总线、DI 均可用），但存在 **4 处内核缺口**需要先补齐：① dataSource 无响应式管理/无撤销；② IRenderer 缺 `setRuntimeConfig` 通道（改数据源画布无法热更新）；③ save 链路不含 dataSource；④ RequestFnSetter/ModelNameSetter 无数据供给。详见第 8 章。

## 1. 调研分析：dataSource 四块数据结构

### 1.1 总体结构

```jsonc
"dataSource": {
  "api":             { "config": {}, "list": { ... } },   // config=全局 axios 基底（新版消费）；list=旧版接口登记表（新版废弃维护，兼容透传）
  "requestConfig":   { [请求名]: RequestConfig },          // 服务配置（url/method 内联于此；渲染层编译为 $requestFns）
  "dataModelConfig": { [模型名]: DataModel },              // 模型配置（编译为 $dataModels）
  "sharedFns":       { [函数名]: { enabled, fn } }         // 共享方法（编译为 $sharedFns）
}
```

### 1.2 requestConfig 项结构（最复杂）

从 order-table-config 的 `loadData` 提取的完整形态：

```jsonc
"loadData": {
  "url": "/demo/receive/getMany",
  "method": "post",
  "config": {},                       // 项级 axios 覆盖（可选）
  "groupName": "默认分组",             // 设计期分组（渲染层忽略）
  "sort": 1,                          // 设计期排序（渲染层忽略）
  "description": "paginationParams分页传参演示",
  "beforeReq": { "enabled": false, "fn": "" },   // 前置拦截（改 axiosConfig）
  "afterReq":  { "isOn": true, "fn": "async function afterReq(responseResult){ return responseResult; }" },
  "paramsConfig": {
    "paramsType": "paginationParams", // kvParams|routeParams|formSaveParams|paginationParams|''
    "dataModelType": "single",        // single|orderItems|items（参数结构：单对象/主从/数组）
    "dataModelName": "receiveFilter", // ← 参数取值的数据模型名（点分根）
    "advancedFilterModelName": "advancedFilter",  // 高级筛选模型名（可选，ledger 用）
    "paginationConfig": { ... },      // 分页参数配置（可选）
    "paramsModel": {                  // ← 表 → 字段 → 参数定义
      "singleTable": {
        "orderBy":     { "valueType": "object", "defaultValue": { "is_audit": "ASC", "created_at": "DESC" } },
        "isRemoved":   { "op": "equals", "valueType": "boolean", "defaultValue": false },
        "orderCode":   { "op": "contains", "valueType": "string" },
        "id":          { "valueType": "number", "resolveType": "routeParams" },
        "isAudit":     { "valueType": "boolean", "resolveType": "bodyParams" },
        "orderId":     { "valueType": "string", "isCache": true }
      }
    }
  }
}
```

**字段级 paramsModel 条目**（编辑器需要表单化的最小单元）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `valueType` | `string/number/boolean/list/object` | 值类型（渲染层做 Number 转换等） |
| `op` | `equals/contains/in/between/gt/gte/lt/lte/ne/notIn/notLike/notBetween` | 查询操作符（仅 paginationParams 的 body 参数会编译成 TypeORM 条件） |
| `defaultValue` | any | 默认值（merge 优先级：全局上下文 > 外部参数 > 页面模型 > 默认值） |
| `resolveType` | `queryParams/routeParams/bodyParams`（可逗号多值） | 参数解析去向；缺省按 paramsType 推断 |
| `isCache` | boolean | 请求时回写到页面模型（跨请求记忆，如 loadItemsData 的 orderId） |
| `isSkipVal` | boolean | 设计期标记：true 时保存不写 defaultValue |

### 1.3 dataModelConfig 结构（两级嵌套 + 两种表形态）

```jsonc
"dataModelConfig": {
  "receiveFilter": {                       // 模型名（modelName 点分路径的根）
    "description": "查询过滤器",            // 设计期描述（builder 跳过此键）
    "singleTable": {                       // 表名（对象形态：字段 → 定义）
      "materialName": { "valueType": "string", "defaultValue": null, "isSkipVal": false },
      "materialModel": { "valueType": "string", "defaultValue": null, "isSkipVal": false }
    }
  },
  "formModel":  { "description": "模型描述", "qReceive": { ...10 字段 } },   // 表单主表
  "detailData": { "description": "详情表格项数据",
    "oriTable": [],      // ← 数组形态：空数组占位（运行时放行数据，编辑器代表"数组表"）
    "serchTable": []
  },
  "listAdvancedViewItems": { "singleTable": [] }   // 高级筛选展示项（数组形态）
}
```

- **对象表** `{字段: {valueType, defaultValue, isSkipVal?}}`：buildDataModel 逐字段按优先级取值（全局上下文 > 注入数据 > defaultValue > valueType 兜底）
- **数组表** `[]`：直接初始化为空数组（高级筛选条件、表格行数据等）
- ledger-config 有 13 个模型，展示真实复杂度：每块 UI 区域一组 filter/advancedFilter/viewItems 三件套

### 1.4 sharedFns 结构

```jsonc
"sharedFns": {
  "searchTable": {
    "enabled": true,                        // ← 新版字段名（旧版 isOn）
    "fn": "function(ctx, payload) { var t = ctx.getNode('YqTableAsync::singleTable'); t.exposed.reloadData({ isReset: true }); }"
  }
}
```

> **格式陷阱**：order-table-config 的 afterReq 用 `isOn`，渲染层 executor 检查的是 `.enabled` —— 旧数据不兼容点之一。新版插件一律写 `enabled`（对齐 single-table-scene.json 与 core-next 类型），读取时兼容 `isOn` 回退。

### 1.5 api 结构

```jsonc
"api": {
  "config": { },                    // 全局 AxiosRequestConfig（baseURL/headers/timeout…），每请求合并基底
  "list": {                         // 旧版设计期接口登记表（渲染层不消费；requestConfig 自带 url/method）
    "supplier-getMany": { "url": "...", "method": "post", "description": "...", "groupName": "...", "sort": 1, "config": {} }
  }
}
```

**v1.1 决策：废弃 `api.list` 独立维护**。旧版「接口」Tab 维护该登记表、服务配置从中选接口（camelCase 生成编码 + 继承描述分组）。实际使用中**接口几乎不存在跨服务复用**（三份 demo 的 api.list 均为空或与 requestConfig 一一对应），独立目录只增加「先登记接口、再关联服务」的两跳成本。新版：

- **服务配置直接内联 url/method**（requestConfig 本就自带，单处编辑即生效）
- `api.config` 全局基底**保留**，入口收编到服务 Tab 列表头部「全局配置」
- `api.list` **兼容透传**：归一化时原样保留在文档中（不展示、不编辑、不删除），避免破坏存量数据；如需清理由宿主在持久化侧处理

## 2. 渲染层消费链路（插件必须产出的契约）

插件产出的每一份数据在渲染侧的编译/执行路径（**这是插件的数据正确性验收标准**）：

### 2.1 requestConfig → $requestFns（`request/executor.ts` createHttpFn）

```
调用 $requestFns[name](params)
  → transformParams(reqConfig, api, params, $dataModels, $globalVars.$context, security):
      axiosConfig = { ...api.config, ...reqConfig.config, url, method }   // ← api.config 是全局基底
      pageModel = deepClone($dataModels[dataModelName])                   // ← 从页面模型取原始表数据
      逐表遍历 paramsModel:
        数组表数据 → bodyData[表名] 原样深拷贝
        mergeRequestParams(表字段配置, $context, 原始表数据, 外部参数)      // ← 参数四源合并
        parseParamsToContainer: 按 resolveType 分发
          routeParams → container.routeData（替换 url 的 :param 占位）
          queryParams → container.queryData（? 查询串）
          bodyParams  → container.bodyData
            （paginationParams + op → buildTypeORMCondition 编译 lambda+值）
            （el.isCache → 回写 $dataModels[dataModelName][表][字段]）
      paramsType=paginationParams → handlePaginationParams（QueryConditionInput: take/skip/orderBy/conditionLambda/conditionValue）
      否则 handleNormalBodyParams（dataModelType=items/orderItems 取单表；single 取全 bodyData）
  → beforeReq?.enabled ? safeEvalFn(fn)(axiosConfig) : 直接
  → axios(axiosConfig)
  → afterReq?.enabled ? fn(result) 包装 : 标准 HttpResult {error,data,code,status,message}
```

**编辑器侧必须保证的约束**（否则运行期静默失败）：

| # | 约束 | 原因 |
|---|---|---|
| R1 | `url` 中 `:param` 占位必须有对应 `resolveType: routeParams` 字段且能从模型/上下文/参数取到值 | `replaceRouteParams` 只替换 container.routeData 里有的键 |
| R2 | `paramsType: paginationParams` 时 op 才会被编译为查询条件；其他类型 op 是死配置 | container.ts L172 |
| R3 | `valueType: number` 的值会强制 `Number()` 转换（'12'→12，''→0 风险） | convertValueType |
| R4 | `valueType: string` + 值为空串的条件在 TypeORM 编译时被丢弃 | buildTypeORMCondition L56 |
| R5 | `isCache` 回写目标模型必须存在该表 | container L158 |
| R6 | beforeReq/afterReq 签名：`async function beforeReq(requestConfig)` / `async function afterReq(responseResult)`，**必须 return** | executor 直接使用返回值 |
| R7 | dataModelName 必须存在于 dataModelConfig（否则 pageModel 空 → 全靠 defaultValue/外部参数） | transform L81 |
| R8 | sharedFns/拦截器 fn 字符串 safeEvalFn 失败 → 静默禁用（sharedFns warn，事件强制 enabled:false） | shared-fn-loader / adapt-node-tree |

### 2.2 dataModelConfig → $dataModels（`data-model-builder.ts`）

- `description` 键跳过；对象表 → 字段级默认值对象；数组表 → `[]`
- `AssemPlugin.install` 用 `reactive()` 包装 → 画布内脚本 `ctx.$dataModels.filter.singleTable.paymentCode = v` 直接驱动 UI

### 2.3 sharedFns → $sharedFns（`shared-fn-loader.ts`）

`enabled:false` 跳过；字符串经 safeEvalFn；失败 warn 并丢弃该函数。

### 2.4 画布同步现状（关键约束）

- **inline（PcRenderer）**：`AssemCore` 在 `app.use(AssemPlugin, config)` 时构造，`dataSource` 在 mount 时定格 —— **当前没有任何热更新通道**
- **iframe（PcIframeRenderer）**：`setRuntime({routerConfig, dataSource, globalVars})` 仅在**连接时下发一次**（DesignerHost mount 前）；`IframeCanvasRenderer.setRuntime` 只是缓存变量，mount 后调用不触发重编译
- 结论：**修改 dataSource 后想让画布生效，现状只能整树 remount**。设计上必须新增渲染器能力（见 9.2）

### 3.2 值得继承的设计

1. **Tab 信息架构**（服务/模型/方法，3 Tab）—— 旧版 4 Tab 中的「接口」Tab 经实际使用验证为低复用（见 1.5 决策），新版收敛合并进服务
2. **服务配置的 key/items 双栏编辑**：paramsModel 天然是「表(key) → 字段(items)」两级结构，左侧 key 列表 + 右侧字段表格是正确交互
3. **模型导入**：从后端 `assem/page-assem-models` 拉取表结构（modelCode/fields/Number|String|DateTime|Boolean → valueType），一键生成字段配置
4. **选择模型带出字段**：编辑请求参数时选 dataModelName 自动填充 paramsModel（字段/类型/默认值预置）
5. **分组/置顶/排序**：大配置集（ledger 15 个共享函数）的检索性保障
6. **默认拦截器代码模板**：`async function beforeReq(requestConfig){ return requestConfig; }`

**不再继承**：接口目录 + 快捷添加弹窗（api.list 树选、RenderAddApiDialog）—— 服务直接内联 url/method 后无存在必要，同时消灭旧版 P1 中「快捷加接口」的耦合逻辑。

### 3.3 问题清单（新版必须解决）

| # | 问题 | 具体表现 |
|---|---|---|
| P1 | **巨石组件** | request-config.tsx 1680 行：列表渲染/分组逻辑/表单校验/paramsModel 编辑/拦截器弹窗/快捷加接口全部内联在一个 setup，methods 对象 40+ 方法 |

| P8 | **isOn/enabled 双写** | 旧版写 isOn，渲染层新契约读 enabled |

## 4. 新版设计目标与原则

1. **数据正确性优先**：产出 100% 对齐 core-next 契约（enabled 字段名、类型化默认值、isSkipVal 语义）
2. **类型化存储层**：编辑态即存储态 —— 引入 `DataSourceDocument` 类型化模型 + 单一 Store，消灭 P4/P6 的往返转换
3. **可撤销**：所有 CRUD 走快照历史（复用/参照 EditorStore.commit 模式）
4. **组件规整**：每个 Tab = 页面组件（纯布局）+ 若干子组件（卡片/编辑器/表格）+ 1 个 composable（状态）；单文件 ≤ 300 行
5. **热更新画布**：改完数据源，画布 $requestFns/$dataModels/$sharedFns 即时重编译（需内核前置改造 9.2）
6. **setter 联动**：RequestFnSetter（表格 requestFn）/ ModelNameSetter（输入框 modelName）自动从数据源取实时选项
7. **宿主可插拔**：后端模型导入、HTTP 客户端经插件 options 注入（编辑器内核不依赖 axios）

## 7. 数据流与状态管理

### 7.1 DataSourceDocument（插件核心 composable）

```ts
/** 与渲染契约 1:1 的类型化文档（对齐 core-next types/datasource） */
export interface DataSourceDocument {
  api: {
    config: Record<string, any>;              // 全局 axios 基底（服务 Tab「全局配置」编辑）
    list: Record<string, ApiItem> | null;     // 旧版接口登记表：兼容透传（不展示/不编辑/不删除），新配置恒为 null
  };
  requestConfig: Record<string, ServiceItem>;      // ServiceItem = core-next RequestConfig（enabled 化拦截器；url/method 内联）
  dataModelConfig: Record<string, ModelItem>;
  sharedFns: Record<string, { enabled: boolean; fn: string }>;
}

function createDataSourceDoc(editor: Editor) {
  // 1. 源：editor.dataSource（构造入参）→ 归一化（isOn→enabled、补 groupName/sort）
  // 2. state = reactive<DataSourceDocument>(normalized)
  // 3. 历史栈：past/future 快照数组（cloneDoc，上限 30）
  //    commit(label, mutator) —— 与 EditorStore.commit 同构
  //    undo()/redo()/canUndo/canRedo
  // 4. 防抖 flush（300ms）：state → editor.dataSource 引用替换
  //    + editor.renderer?.setRuntimeConfig({ dataSource: cloneDoc(state) })
  //    + bus.trigger('ds:changed', { sections: ['requestConfig'] })
  // 5. dispose：清定时器
}
```

**决策记录**：

- **历史独立于 schema 撤销栈**：dataSource 与 uiSkeleton 语义不同（数据配置 vs 界面结构），合入主栈会导致「拖个按钮也回滚数据源」的怪异体验。独立 30 步快照，面板头部放撤销/重做按钮。
- **编辑落地策略**：Drawer 内表单是本地草稿（el-form model），点保存才 `doc.commit()`；列表上的轻操作（enabled 直切/置顶）即时 commit。
- **归一化只读兼容**：`isOn ?? enabled` 读取；写入一律 enabled。`api.list` 原样透传（v1.1）。

### 7.2 变更传播全景

```
Drawer 保存 ─→ doc.commit(label, mutator)
                ├─ pushHistory(cloneDoc)
                ├─ mutator(state)            （reactive）
                └─ scheduleFlush()

                          state 深拷贝 → editor.dataSource = clone   （宿主 getSchema 持久化取到）

setter 选中 ←──────────────────────────────┘（ModelNameSetter/RequestFnSetter 重算选项树）
```

## 9. 编辑器内核增强清单（前置改造）

### 9.1 dataSource 响应式归属（小）

保持 `editor.dataSource` 为**引用替换式**（doc flush 时整体换引用），不放进 `store.state`（避免与 schema 历史混淆）。补充 `Editor.getDataSource(): deepClone` 便捷方法。

### 9.2 IRenderer 新增 setRuntimeConfig（关键）

```ts
// scenario/types.ts IRenderer 增补
/** 运行时配置热更新（dataSource 等）；实现方须保证幂等与重编译 */
setRuntimeConfig?: (payload: { dataSource?: any; globalVars?: Record<string, any> }) => void;
```

三个实现点：

1. **PcRenderer（inline）**：持有 `this.core`（AssemCore）。实现 = `core.reinit({...config, dataSource: 新值})` + `reactive` 重新包装 + re-provide 难点 —— 由于 provide 在 install 时发生，**简化方案：保存当前 schema → unmount → 重新 mount**（复用现成装配链，代价 ~100ms，配置场景可接受；二期再做 core.reinit 增量路径）
2. **IframeCanvasRenderer（iframe 内）**：`setRuntime(payload)` 已存在但 mount 后不生效 → 增补：`setRuntimeConfig` 更新 runtimeConfig 后执行「syncSchema(当前 schema) + 重建 app（mount()）」；协议 `IframeRendererApi` 增加同名方法
3. **PcIframeRenderer（Host 侧）**：透传 `rendererApi.setRuntimeConfig?.(payload)`，未连接时合并进 `this.runtimeConfig`

## 10. setter 联动设计

现状：`element-table.ts` 的 `requestFn` 已配 `setter: "RequestFnSetter"`、`modelName` 配 `setter: "ModelNameSetter"`，但 setterProps 无数据 → 两个 setter 显示空树。

方案（不破坏静态 setterProps 语义）：

1. `setters/base.ts` 的 `useSetterCtx()` 已向所有 setter 注入 `{editor, setterRegistry, nodeId}`
2. 增强 `RequestFnSetter`：props.dataSourceTree 为空时，从 ctx.editor 构建选项树 —— `dataSource.requestConfig` 按 groupName 分组 → `[{id, description, isGroup, children}]`，计算属性响应 `ds:changed` 事件重建
3. 增强 `ModelNameSetter`：props.modelTree 为空时，从 `dataSource.dataModelConfig` 构建 `{key: 模型名, description, children: [{key: 表名, children: [{key: 字段, fullPath: '模型.表.字段', isLeaf: true}]}]}`（fullPath 即节点 modelName 点分路径，与 useInputValue 寻址一致）
4. 插件 setup 里向 bus 订阅无关侵入 —— 树构建逻辑放 setter 内部 computed，依赖 `editor.dataSource` 引用替换即自动重算（flush 换引用天然触发）
